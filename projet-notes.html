Projet

Gestionnaire de notes sécurisé

Une application web où chaque utilisateur crée et gère ses notes privées. L'objectif n'était pas la fonctionnalité en elle-même, mais d'apprendre à construire une application qui résiste aux attaques, puis de le prouver en l'attaquant moi-même.

  • Python
  • Flask
  • SQLite
  • Argon2
  • 2FA / TOTP
  • pytest
  • Docker
  • nginx
  • redis

Fonctionnalités

Comptes

Inscription, connexion, changement de mot de passe, suppression du compte avec effacement réel des données.

Double authentification

Codes TOTP (Google Authenticator, Aegis…) via QR code, et 10 codes de secours à usage unique, régénérables.

Sessions

Déconnexion de tous les autres appareils, automatique après un changement de mot de passe.

Journal de sécurité

Chaque utilisateur voit l'activité de son compte (connexions, échecs, blocages) et peut repérer une intrusion.

Attaques bloquées

Pour chaque attaque, au moins un test automatisé tente l'attaque et vérifie qu'elle échoue.

AttaqueProtection
Injection SQLRequêtes paramétrées, jamais de SQL construit à partir d'une saisie
XSSÉchappement automatique des templates + Content-Security-Policy stricte
CSRFJeton dans chaque formulaire, actions sensibles uniquement en POST

Déploiement

Trois conteneurs Docker, organisés comme un vrai serveur de production :

Navigateur ──HTTPS──▶ nginx ──▶ app (Flask + gunicorn) ──▶ redis
                     (TLS)     réseau interne, sans accès à Internet
  • HTTPS uniquement, TLS 1.2 et 1.3, protection contre Slowloris
  • Conteneurs sans root, système de fichiers en lecture seule, aucun privilège Linux
  • L'application n'a pas accès à Internet : impossible d'exfiltrer des données
  • Ports ouverts uniquement en local (Docker contourne le pare-feu ufw)

Ce que j'ai appris

Tester le vrai déploiement

Les 73 tests passaient, mais derrière nginx tous les formulaires étaient refusés : le port disparaissait de l'en-tête Host. Seule une attaque contre le déploiement réel l'a révélé.

Une protection peut créer une faille

Bloquer un compte après 5 échecs permet à un attaquant de bloquer n'importe qui. D'où un blocage progressif plafonné, et des échecs comptés même pour les noms inexistants.

Supprimer n'est pas effacer

Avec SQLite, une note « supprimée » restait lisible dans le fichier avec strings. Ma machine l'effaçait par défaut, une autre non : il ne faut pas dépendre des réglages par défaut.

Vérifier les outils

Un « 0 problème » de bandit ne prouve rien : je l'ai d'abord testé sur un fichier volontairement vulnérable, et j'ai trouvé ses angles morts.
